# 最小代码实现

## 目标与范围

这是一份跨编程语言的用户级通用规则，适用于创建、修改和重构代码。目标是在完整满足
当前契约和验收条件的前提下，实现最少的对外接口、状态、分支、抽象和错误处理。

本规则不代替项目架构、语言规范、安全要求或代码审查规则。简单不是单独目标，不得为
减少代码而破坏正确性、安全性、资源释放、数据一致性或明确要求的兼容性。

## 1. 先确定契约

实现前 MUST 从用户需求、项目规则、现有接口、调用方和测试中确定：

- 必须提供的操作和对外可见符号；
- 有效输入、输出、状态变化和副作用；
- 必须处理的错误及其可观察语义；
- 与当前任务相关的所有权、生命周期、并发和资源约束。

现有契约能够确定行为时，MUST 遵循现有契约。缺失信息只有在会实质改变对外接口、
可观察行为或关键数据模型时才需要询问；不得自行扩展契约。

## 2. API 完整但不扩张

API 包括供其他代码、模块、进程或用户调用和依赖的函数、方法、类型、数据格式、命令、
事件及其他可观察接口。

API MUST 完整表达当前任务要求的能力，但不得包含没有当前调用方、既有契约或明确需求的：

- 预留参数、配置项和扩展点；
- 未来可能使用的公共方法、类型或状态；
- 多套功能等价的入口；
- 为假设性替换、兼容或迁移准备的包装层。

能通过现有 API 完成任务时，MUST NOT 新增对外接口。API 完整是指当前契约完整，不是为
未知未来提供更多能力。

## 3. 实现最小充分路径

实现 MUST 只包含：

- 完成契约所需的主路径；
- 契约明确要求的错误路径；
- 可达且有依据的失败模式所需的处理；
- 正确释放资源和维持数据一致性所需的逻辑。

每个新增分支、状态、校验、转换层或抽象都 MUST 能追溯到需求、既有契约、实际调用路径
或已复现的故障。无法追溯时不得加入。

优先使用一个直接实现，不得为假设性复用增加抽象。新增抽象必须由当前契约、项目架构
或可证明的整体复杂度降低所要求；代码重复本身不足以证明需要抽象。

## 4. 边界与错误处理

只在数据进入当前责任范围或跨越信任边界时执行必要校验。某个不变量在边界建立后，
内部可信调用链 MUST NOT 重复验证或为其增加兜底分支。

错误 MUST 按当前语言、框架和项目的既有契约传播、返回、记录或终止。除非需求、契约或
已确认的故障模式要求，MUST NOT：

- 吞掉错误或异常；
- 用默认值、空结果或成功状态掩盖失败；
- 静默忽略失败；
- 自动重试、降级或切换实现；
- 同时维护主要路径和备用路径；
- 捕获当前层无法正确处理的宽泛错误；
- 为违反内部不变量的状态继续执行。

必要的输入校验、安全检查、资源清理和一致性保护属于正确性要求，不视为冗余兜底。

## 5. 控制修改范围

MUST 只修改完成当前任务所需的文件、符号和调用路径。不得顺便：

- 清理无关技术债；
- 统一无关代码风格；
- 重构没有阻碍当前任务的代码；
- 增加未来功能；
- 扩大兼容平台或运行环境；
- 改变无关 API 或数据模型。

发现无关问题时可以报告，但不得自动修改。

## 6. 验证与停止

验证 MUST 覆盖当前契约、改动路径和已修复的具体故障。优先运行项目已有的格式检查、
构建、静态分析和相关测试，不为假设性风险无限增加测试、保护代码或审查轮次。

以下条件全部满足时 MUST 停止实现：

- 当前 API 契约完整；
- 验收条件已经满足；
- 必要验证已经通过；
- 没有已知的可达正确性问题。

后续审查遵循适用的代码审查规则，不因非阻塞建议继续修改。
