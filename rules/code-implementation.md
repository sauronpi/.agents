# 最小充分代码实现

## 目标与范围

这是一份跨编程语言的用户级通用规则，适用于创建、修改和重构代码。目标是在完整满足
当前契约和验收条件的前提下，避免无依据的对外接口、状态、分支、抽象和错误处理。

本规则不代替项目架构、语言规范、安全要求或代码审查规则。简单不是单独目标，不得为
减少代码而破坏正确性、安全性、资源释放、数据一致性或明确要求的兼容性。

## 1. 先确定契约

实现前 MUST 按当前任务需要，从用户需求、项目规则、现有接口、调用方和测试中确定：

- 必须提供的操作和对外可见符号；
- 有效输入、输出、状态变化和副作用；
- 必须处理的错误及其可观察语义；
- 与当前任务相关的所有权、生命周期、并发和资源约束。

当前任务未明确要求改变的既有契约，MUST 保持。缺失信息只有在
会实质改变对外接口、可观察行为、关键数据模型或正确性约束时才需要询问。

## 2. API 完整但不扩张

API 包括供其他代码、模块、进程或用户调用和依赖的函数、方法、类型、数据格式、命令、
事件及其他可观察接口。

API MUST 完整表达当前任务要求的能力，但不得包含没有当前调用方、既有契约或明确需求的：

- 为未来需求预留的参数、配置项、扩展点、公共方法、类型或状态；
- 多套功能等价的入口；
- 为假设性替换、兼容或迁移准备的包装层。

## 3. 实现最小充分路径

实现 MUST 采用完成当前契约所需的直接路径。仅在满足当前需求、既有契约或处理
有依据且可达的故障所必需时，才新增分支、状态、校验、转换层或抽象。
代码重复本身不足以证明需要抽象。

## 4. 边界与错误处理

在数据进入当前责任范围、跨越信任边界，或需要建立或重新确认不变量时执行必要校验。
某个不变量已经建立且仍然有效时，内部可信调用链 MUST NOT 重复验证或增加兜底分支。

错误 MUST 按当前语言、框架和项目的既有契约传播、返回、记录或终止。MUST NOT：

- 无契约依据地忽略错误，或以默认值、空结果、成功状态掩盖失败；
- 无当前层职责依据地捕获宽泛错误；
- 在所需内部不变量不成立时，继续执行依赖该不变量的操作。

## 5. 控制修改范围

MUST 只修改完成当前任务所需的文件、符号和调用路径。不得顺便清理无关技术债、统一
无关代码风格、重构没有阻碍当前任务的代码，或扩大任务之外的兼容平台和运行环境。

发现无关问题时可以报告，但不得自动修改。

## 6. 验证与停止

验证 MUST 覆盖验收条件、受改动影响的契约、改动路径和已修复的具体故障。优先运行项目
已有的格式检查、构建、静态分析和相关测试，不为假设性风险无限增加测试、保护代码或
审查轮次。

以下条件全部满足时 MUST 停止实现：

- 当前验收条件和受改动影响的契约已经满足；
- 必要验证已经通过；
- 当前任务范围内，改动及其直接影响路径中没有已知的可达正确性问题。

必要验证受阻且无法在当前授权范围内解决时，MUST 停止修改，说明阻碍、未验证项及其
影响，不得宣称验证通过。
