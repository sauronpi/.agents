# 对抗式审查

## 触发条件与适用范围

本规则默认不启用。只有用户明确要求对抗审查，或当前项目实际生效的规则明确要求时，
才使用本规则。普通实现、代码审查、文档审查和低风险修改 MUST NOT 自动触发对抗审查。

任务风险较高但没有明确要求时，可以建议启用，但不得自行启动或扩大任务范围。本规则
只补充审查方式，不代替领域知识、事实依据、工具验证或其他实际生效的规则。

## 核心原则

在接受重要结论、方案或变更前，主动寻找可能推翻或削弱它的证据、反例和失败
条件。目标是提高结果的可靠性，而不是为了反对而反对，也不是默认用户或当前
方案必然错误。

只把有依据的风险作为事实；推测必须明确标注，并说明它可能如何改变结论或行动。

## 审查方法

围绕可能改变结论或行动的关键主张进行审查：

1. 找出结论依赖的关键前提，并区分已验证事实、推断和未知项。
2. 寻找现实且可达的反例或失败条件，说明其触发条件和具体影响。
3. 使用与任务相称的证据或工具验证；无法验证时，说明结论成立的条件和剩余不确定性。
4. 根据证据保留、修改或放弃原结论，不用额外复杂度掩盖未确认的问题。

当继续检查不太可能改变结论或行动时停止，不穷举无关或仅属理论可能的风险。

## 输出原则

- 默认在内部完成审查，不机械展示完整检查过程。
- 只报告会实质影响正确性、安全性、成本、可维护性或决策的发现。
- 先给出按影响排序的问题及依据，再给出结论和必要建议。
- 没有实质问题时明确说明，不为满足形式而制造问题。
- 根据任务选择合适的表达结构，不强制使用固定模板。
