# 通用 C 代码风格

## 适用范围

这是一份用户级共享 Rule，适用于创建、修改、重构或审查人工维护的 `.c` 和 `.h`
文件，包括普通 C、嵌入式 C 以及同一项目内参与 C/C++ 混合编译的 C 代码。

第三方代码、生成代码和项目明确排除的目录不适用本 Rule。独立的 C++、Objective-C
及其他语言文件应遵循各自的项目规范，不得仅为与 C 代码统一而改成 snake_case。

执行相关任务前，MUST 读取
[`../skills/c-code-style/references/style-guide.md`](../skills/c-code-style/references/style-guide.md)。
创建、修改、重构或审查 C 代码时，`c-code-style` Skill 可用则 MUST 使用其工作流。

## 项目配置

项目级规则入口 SHOULD 声明：

- C 标准，未声明时默认 C99；
- C++ 混编检查标准，未声明时默认 C++11；
- 公共符号的小写前缀和常量的大写前缀；
- C 与 C++ 编译器，以及 formatter、lint、构建和测试命令；
- 需要由 C++ 包含的共享头文件；
- 项目例外和不适用目录。

公共前缀未声明时，先从现有公共 API 一致地推断。无法可靠推断且任务需要新增公共
符号时，MUST 在命名前询问用户。没有公共 API 的项目 MAY 明确声明无需公共前缀。

## 优先级

按以下顺序处理冲突：

1. 用户对当前任务的明确要求；
2. 项目规则、语言标准、平台约束和工具配置；
3. 邻近且仍有效的 C 代码风格；
4. 共享风格参考中的默认规则。

存在 `.clang-format` 或等效项目 formatter 时，机械排版 MUST 服从该配置。Linux
内核等具有强制规范的项目 MUST 使用其原生规范，不得强制应用共享的 `_type` typedef
或默认排版。

## 修改边界

- 修改既有文件时只调整当前任务直接涉及的代码，不顺便统一无关格式或命名。
- 验证 MUST 遵循 `c-code-style` Skill；无法执行必要检查时，MUST 说明原因和剩余风险。
