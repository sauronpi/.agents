# C Code Style

按项目约束和共享规范处理 C 代码，同时避免扩大格式化、重命名或语言兼容范围。
本 Skill 及其参考资料中的风格约定依次服从用户当前要求、项目规则与工具配置、邻近代码
惯例、本 Skill 默认值；语言、接口和硬件的正确性要求不因风格优先级而放宽。

## 工作流程

### 1. 确定作用域与项目约束

1. 读取实际生效的项目规则。
2. 根据用户请求和项目证据确定目标是人工维护的 `.c` 或 `.h`，排除第三方、生成代码及项目明确排除的目录。
3. 按任务需要补充上下文：排版查 formatter 配置与命令；新增公共符号查项目前缀；
   语法、兼容性或构建验证查相关语言标准、编译器、构建文档和编译配置。
4. 读取目标文件及邻近 C 文件，识别项目已有风格和接口惯例。
5. 按任务读取直接相关的参考资料：
   - 创建、修改或审查标识符时，读取 [`references/naming.md`](references/naming.md)；
   - 处理 C/C++ 共享头文件或 `extern "C"` 时，读取
     [`references/shared-headers.md`](references/shared-headers.md)；
   - 处理嵌入式、寄存器、并发或可移植性问题时，读取
     [`references/embedded-portability.md`](references/embedded-portability.md)；
   - 新建源文件或头文件，或任务涉及文件组织、声明形式及排版时，读取
     [`references/formatting.md`](references/formatting.md)。

### 2. 创建或修改代码

- 新代码遵循共享规范以及项目已确认的语言标准和 formatter。
- 既有代码只修改任务直接涉及的符号和排版；不要为统一风格重命名公共 API 或格式化
  无关文件。
- 新增公共符号而项目无前缀约定时，依据项目或模块名称选择并说明。仅当按上述优先级
  仍无法从项目证据可靠消解约定冲突，或兼容性不确定性会实质影响当前接口时，提供备选
  方案并询问用户。
- 仅在任务需求或已确认的项目环境支持时，引入操作系统服务、动态内存或编译器扩展。

### 3. 审查代码

仅要求审查时默认只报告，不直接修改；请求明确包含修改或修复时，按该授权执行。每个问题
说明位置、违反的项目或共享规则、实际影响和最小修复。仅风格偏差不得冒充正确性缺陷；
如果用户明确要求风格合规审查，则按该验收目标报告全部可证明的偏差。

### 4. 验证

按变更影响选择以下检查；优先使用项目已有检查，已有等价覆盖时不重复构造验证用例。

1. 对受影响文件运行项目 formatter 的检查模式，不使用会改写无关文件的全仓库命令。
2. 运行与变更相关的项目 lint、静态分析、构建和测试。
3. 变更可能影响 C/C++ 共享接口时，按
   [共享头文件验证要求](references/shared-headers.md#验证)执行对应检查。
4. 报告实际执行的命令、结果、未执行检查和剩余限制。

临时验证文件 MUST 位于系统临时目录或项目忽略的构建目录，不得写入受版本控制的源码
目录。
