# C Code Style

按项目约束和共享规范处理 C 代码，同时避免扩大格式化、重命名或语言兼容范围。

## 工作流程

### 1. 确认作用域与项目约束

1. 读取实际生效的项目规则、构建文档和编译配置。
2. 确认目标是人工维护的 `.c` 或 `.h`，排除第三方、生成代码及项目明确排除的目录。
3. 查找 `.clang-format`、formatter 命令、C/C++ 标准、编译器、公共符号前缀和共享头文件
   清单。
4. 读取目标文件及邻近 C 文件，确认项目已有风格和接口惯例。
5. 每次执行都完整读取 [`references/style-guide.md`](references/style-guide.md)。

### 2. 创建或修改代码

- 新代码遵循共享规范以及项目已确认的前缀、语言标准和 formatter。
- 既有代码只修改任务直接涉及的符号和排版；不要为统一风格重命名公共 API 或格式化
  无关文件。
- 公共前缀无法可靠确定且需要新增公共符号时，先询问用户。
- 不默认引入操作系统、动态内存或编译器扩展。
- 修改 C/C++ 共享头文件时，使用规范中的条件化 `extern "C"` 结构，并保持头文件
  自包含。

### 3. 审查代码

审查任务默认只报告，不直接修改。每个问题说明位置、违反的项目或共享规则、实际影响
和最小修复。仅风格偏差不得冒充正确性缺陷；如果用户明确要求风格合规审查，则按该验收
目标报告全部可证明的偏差。

### 4. 验证

1. 对受影响文件运行项目 formatter 的检查模式，不使用会改写无关文件的全仓库命令。
2. 运行项目已有 lint、静态分析、构建和相关测试。
3. 对受影响的 C/C++ 共享头文件分别创建临时 `.c` 和 `.cpp` 包含单元，并使用项目指定
   的标准执行语法编译。
4. 项目已有混合链接测试时运行该测试；没有时，仅在当前任务涉及 `extern "C"` 或新增
   跨语言调用时构造最小的 C 实现与 C++ 调用方链接检查。
5. 报告实际执行的命令、结果、未执行检查和剩余限制。

临时验证文件 MUST 位于系统临时目录或项目忽略的构建目录，不得写入受版本控制的源码
目录。

## Gotchas

- typedef 使用 `_type`，不要使用 POSIX 保留的 `_t` 后缀。
- `extern "C"` 只放在条件化的共享头文件声明周围，不写入 `.c` 实现。
- 不因 C 使用 snake_case 而重命名同项目中的 C++ 符号。
- 不用共享的 Allman 默认覆盖 `.clang-format`、邻近项目风格或 Linux 内核规范。
- 不将 C++ 头文件兼容扩展为其他语言互操作或跨工具链保证。

## 触发边界示例

应该触发：

- “为这个嵌入式模块新增 `.c` 和 `.h`。”
- “把这个公共 C 头文件改成可由 C++ 包含。”
- “审查本次 C 驱动修改是否符合项目代码风格。”

不应该触发：

- “重构这个纯 C++ 类。”
- “调整 Objective-C 方法命名。”
- “为 Rust 生成 C ABI 绑定。”
