# Skill Authoring

创建可复用、可触发、可验证且跨 Agent 客户端兼容的 Skill。

## 核心原则

- 从真实任务、失败案例和用户纠正中提炼能力。
- 只写 Agent 在没有该 Skill 时容易遗漏或做错的内容。
- 提供明确的默认做法、关键陷阱和验证闭环。
- 根据任务脆弱程度决定约束强度，保留必要的判断空间。
- 保持 `SKILL.md` 精简，详细资源按需加载。

## 工作流程

### 1. 判断内容应该放在哪里

创建 Skill 前先确认它能解决重复出现的真实问题，并按以下边界放置内容：

- 跨项目复用的专业知识或工作流：全局 Skill。
- 只适用于单个项目的专业流程：项目级 Skill。
- Agent 的通用工作方式和行为约束：`AGENTS.md`。
- 项目背景、架构和业务说明：项目文档。
- 可机械检查或重复执行的逻辑：linter、validator、test 或 script。

如果 Agent 无需额外指令就能可靠完成任务，或者现有工具能直接解决问题，不要创建 Skill。

### 2. 收集证据并定义边界

新建或大幅修改 Skill 时，收集：

- 2 至 3 个应该触发的真实请求。
- 至少 1 个不应该触发的相邻请求。
- 预期输入、输出和成功标准。
- Agent 容易犯的具体错误或用户纠正。
- 所需工具、环境和验证方式。

从案例中提取可复用流程，不要写入某次任务的具体答案。让一个 Skill 覆盖一个连贯工作单元：过窄会迫使相关 Skill 同时加载，过宽则难以准确触发。

### 3. 编写触发描述

`description` 必须同时说明 Skill 做什么，以及什么请求、文件、工具或场景应触发它。

- 使用用户请求中可能出现的具体关键词。
- 覆盖主要任务类型，不只复述一个示例。
- 避免“提供帮助”“遵循最佳实践”等空泛表述。
- 不依赖正文补充触发条件；正文只在 Skill 触发后加载。

完成后使用正例和反例检查触发边界。

### 4. 组织资源

每个 Skill 必须包含 `SKILL.md`。开放格式允许附加任意文件和目录，常用约定为：

```text
skill-name/
├── SKILL.md
├── scripts/
├── references/
└── assets/
```

- `SKILL.md`：每次触发都需要的步骤、选择规则和关键陷阱。
- `scripts/`：需要确定性执行或每次都会重复实现的代码。
- `references/`：只在特定条件下读取的详细规范和知识。
- `assets/`：生成最终产物所需的模板、图片、字体或数据。

本仓库默认不创建空目录、README、变更日志、占位文件或重复说明；只有 Agent 执行任务确实需要时才增加资源。

### 5. 编写正文

使用命令式、可执行的说明：

- 给出默认方案，只在条件满足时介绍替代方案。
- 对脆弱、不可逆或顺序敏感的操作给出精确步骤。
- 使用短示例或模板表达固定输出格式。
- 把违反合理预期的事实和常见错误放在 Gotchas 中。
- 需要产出文件时说明输出路径、格式和验证方法。

不要重复基础概念、罗列大量同等选项，或使用无法验证的“正确处理”“注意质量”等要求。

### 6. 设计渐进式披露

`SKILL.md` 只保留每次执行都需要的内容。引用其他资源时：

- 使用相对于 Skill 根目录的路径。
- 明确说明读取或运行条件。
- 让必要资源直接从 `SKILL.md` 到达，避免深层引用链。
- 不在 `SKILL.md` 和 `references/` 重复维护相同内容。
- 为较长的 reference 提供目录或搜索关键词。

### 7. 修改或审查现有 Skill

修改前：

1. 完整读取 `SKILL.md`。
2. 读取本次任务需要的直接引用。
3. 检查现有案例、脚本、验证方式和未提交修改。
4. 分别判断格式、触发和输出质量问题。
5. 保留没有证据需要改变的内容。

优先最小修改，不顺便重构无关目录。审查跨客户端 Skill 时，将客户端扩展与开放格式要求分开判断。

## 格式核心

`SKILL.md` 必须包含 YAML Frontmatter 和 Markdown 正文。默认只使用：

```yaml
---
name: skill-name
description: 描述 Skill 做什么，以及什么时候使用
---
```

`name` 必须满足：

- 长度为 1 至 64 个字符。
- 只包含小写字母、数字和连字符。
- 不以连字符开头或结尾，不包含连续连字符。
- 与父目录名称完全一致。

`description` 必须非空且不超过 1024 个字符，并同时描述能力和触发条件。

可选标准字段包括：

- `license`：许可证名称或 Skill 内许可证文件。
- `compatibility`：环境要求，存在时为 1 至 500 个字符。
- `metadata`：字符串键到字符串值的映射。
- `allowed-tools`：实验字段，各客户端支持不一致；跨客户端 Skill 默认不使用。

将 `SKILL.md` 控制在 500 行和约 5000 tokens 以内。客户端专属元数据不得冒充通用字段；官方 [Agent Skills specification](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx) 是格式解释的最终依据，但 Skill 的日常执行不应依赖联网读取它。

## 分级验证

所有修改都必须：

1. 检查目录名、文件名和 Frontmatter。
2. 运行仓库现有 Markdown linter。
3. 环境中存在 `skills-ref` 时运行 `skills-ref validate path/to/skill`。
4. 实际执行所有新增或修改的脚本。
5. 修复发现的问题并重新验证。

新建或大幅修改时还必须使用真实请求检查执行过程、最终输出以及正反触发边界。复杂 Skill 应比较启用和未启用 Skill 的结果，确认 Skill 带来可观察改进。

格式验证只能证明 Skill 可被读取，不能证明它有效。无法执行的验证必须在交付时说明。

## 审查与交付

审查 Skill 时至少报告：

- 格式合规：Frontmatter、命名、目录和通用字段。
- 触发质量：能力描述、正例覆盖和误触发风险。
- 内容质量：流程可执行性、资源分层、关键陷阱和维护成本。
- 验证缺口：已执行、失败或尚未执行的检查。

为问题引用具体文件位置。修改全局 Skill 后还要说明修改目的、解决的真实问题、为什么适合跨项目复用、为什么不是项目级内容，以及验证结果。
