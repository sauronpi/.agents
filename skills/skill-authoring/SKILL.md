# Skill Authoring

## 工作流程

先区分创建、修改和审查。创建时按以下步骤执行；修改或审查时仅应用相关步骤。仅要求审查
时默认只读；请求明确包含修改或修复时，按该授权执行。

修改或审查前，完整读取 `SKILL.md` 及本次任务需要的直接引用；按影响范围检查相关案例、脚本、验证方式和未提交修改。只修改有证据支持的问题，不顺便重构无关目录。

### 1. 判断内容应该放在哪里

创建 Skill 前先确认它解决真实且可复用的需求，并按以下边界放置内容：

- 可复用的专业知识或工作流：Skill；按使用范围和分发需求选择用户级或项目级，只服务单个项目的流程放在项目内。
- 单个仓库或目录的维护方式和行为约束：该作用域内的 `AGENTS.md`。
- 需要跨项目复用的 Agent 通用工作方式和行为约束：共享 Rule。
- 项目背景、架构和业务说明：项目文档。
- 可机械检查或重复执行的逻辑：linter、validator、test 或 script。

如果 Agent 使用现有知识和工具即可可靠完成任务，不要创建 Skill。

### 2. 收集证据并定义边界

新建或大幅修改 Skill 时，收集：

- 应该触发的代表性请求；存在相邻能力混淆时补充反例。
- 预期输入、输出和成功标准。
- Agent 容易犯的错误或用户纠正，以及所需工具、环境和验证方式。

从案例中提取一个连贯、可复用的工作单元，不写入单次任务答案。

### 3. 编写触发描述

`description` 必须独立说明 Skill 做什么、何时使用，不依赖正文才能判断是否适用。

- 只列 Skill 直接支持、用户可独立请求的主要任务、产物或场景；不写执行步骤、非核心辅助检查或空泛表述。
- 对象使用用户会说出的具体名称，必要时包括文件名、扩展名、格式、协议、框架或工具名。
- 只在有助于选择 Skill 时补充核心约束；只在容易误触发时补充相邻排除范围。

示例：

```yaml
description: '创建、修改、重构或审查通用 C 与嵌入式 C 的 .c/.h 文件。适用于 C 实现、C API、驱动和 C/C++ 共享头文件；不适用于独立 C++ 或 Objective-C 文件。'
```

### 4. 组织资源

开放格式允许按需添加附加资源，常用约定为：

- `scripts/`：需要确定性执行或每次都会重复实现的代码。
- `references/`：只在特定条件下读取的详细规范和知识。
- `assets/`：生成最终产物所需的模板、图片、字体或数据。

仅按任务需要添加资源，避免空目录、占位文件和重复说明。

### 5. 编写正文并渐进披露

使用命令式、可执行的说明，并按操作风险决定精确程度：

- 给出默认方案，只在条件满足时介绍替代方案。
- 对脆弱、不可逆或顺序敏感的操作给出精确步骤。
- 使用短示例或模板表达固定输出格式。
- 在相关步骤旁说明违反合理预期的事实和常见错误，必要时集中成节。
- 需要产出文件时说明输出路径、格式和验证方法。
- `SKILL.md` 保留核心流程和简短的条件说明，建议少于 500 行、约 5000 tokens；仅将较长、低频或独立的资料放入按需读取的资源，不为满足篇幅指标机械拆分。
- 资源使用相对路径并注明读取条件，保持从 `SKILL.md` 直接可达；较长的 reference 提供目录或搜索关键词。

不要重复基础概念或资源内容、罗列大量同等选项，或使用无法验证的“正确处理”“注意质量”等要求。

## 格式核心

`SKILL.md` 必须包含 YAML Frontmatter 和 Markdown 正文。默认只使用：

```yaml
---
name: skill-name
description: '描述 Skill 做什么，以及什么时候使用'
---
```

`name` 必须满足：

- 长度为 1 至 64 个字符。
- 只包含小写字母、数字和连字符。
- 不以连字符开头或结尾，不包含连续连字符。
- 与父目录名称完全一致。

`description` 必须非空且不超过 1024 个字符。

可选标准字段包括：

- `license`：许可证名称或 Skill 内许可证文件。
- `compatibility`：环境要求，存在时为 1 至 500 个字符。
- `metadata`：字符串键到字符串值的映射。
- `allowed-tools`：实验字段，各客户端支持不一致；跨客户端 Skill 默认不使用。

客户端专属元数据不得冒充通用字段；官方 [Agent Skills specification](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx) 是格式解释的最终依据，但 Skill 的日常执行不应依赖联网读取它。

## 分级验证

按变更范围验证：

1. 对受影响的 Markdown 文件优先运行项目已有 linter；不可用时人工检查并报告验证缺口。
2. 新建 Skill、重命名目录或入口文件、修改 Frontmatter 时，检查命名和 Frontmatter。环境中存在 `skills-ref` 时运行 `skills-ref validate path/to/skill`，否则人工检查；工具已覆盖并通过的项目不重复人工检查。
3. 在安全测试环境中执行新增或修改的脚本；无法执行时说明原因，不以静态检查冒充执行结果。
4. 修改任务中，修复本次变更新增的问题并重新验证。无关既有问题单独报告。

新建或大幅修改时，使用“收集证据并定义边界”中收集的案例检查触发边界、执行过程和最终输出。效果不明确时，再比较启用和未启用 Skill 的结果，确认是否带来可观察改进。

格式验证不等于客户端加载验证，也不能证明 Skill 有效。

## 交付

交付时简要报告实际发现、修改和验证结果，注明未执行的检查，并为问题引用具体文件位置。新建全局 Skill 或改变其适用范围时，再说明跨项目复用的依据。
