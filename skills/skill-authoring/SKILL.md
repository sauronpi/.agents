# Skill Authoring

## 工作流程

### 1. 判断内容应该放在哪里

创建 Skill 前先确认它能解决重复出现的真实问题，并按以下边界放置内容：

- 跨项目复用的专业知识或工作流：全局 Skill。
- 只适用于单个项目的专业流程：项目级 Skill。
- Agent 的通用工作方式和行为约束：`AGENTS.md`。
- 项目背景、架构和业务说明：项目文档。
- 可机械检查或重复执行的逻辑：linter、validator、test 或 script。

如果 Agent 无需额外指令就能可靠完成任务，或者现有工具能直接解决问题，不要创建 Skill。

### 2. 收集证据并定义边界

新建或大幅修改 Skill 时，收集：

- 2 至 3 个应该触发的真实请求和至少 1 个相邻反例。
- 预期输入、输出和成功标准。
- Agent 容易犯的错误或用户纠正，以及所需工具、环境和验证方式。

从案例中提取一个连贯、可复用的工作单元，不写入单次任务答案；范围过窄会迫使相关 Skill 同时加载，过宽则难以准确触发。

### 3. 编写触发描述

`description` 必须同时说明 Skill 做什么，以及什么请求、文件、工具或场景应触发它。

- 只列用户可以独立请求且 Skill 直接处理的动作。优先使用“创建、修改、重构、修复、审查、解释、转换、验证”并按此顺序排列；审查默认表示只读检查。领域有更常用且语义不同的动作词时可以例外，不要只为统一措辞替换。
- 对象使用用户会说出的具体名称，必要时包括文件名、扩展名、格式、协议、框架或工具名。
- 正向范围以“适用于”开头，列出主要任务、产物或场景，不写执行步骤。
- 只在有助于选择 Skill 时补充核心约束；只在容易误触发时补充相邻排除范围。
- 不列 Skill 不支持的动作或非核心辅助检查，不使用“提供帮助”“遵循最佳实践”等空泛表述。
- 触发条件全部写入 `description`，不依赖触发后才加载的正文补充。

使用以下模板起草：

```yaml
description: '<主要动作><对象>。适用于<任务、产物或场景>。'
```

必要时在对象后添加“并 `<核心能力或约束>`”，或在句末添加“不适用于 `<相邻范围>`”；最终删除所有占位符。

示例：

```yaml
description: '创建、修改、重构或审查通用 C 与嵌入式 C 的 .c/.h 文件，并按项目既有规则验证。适用于 C 实现、C API、驱动和 C/C++ 共享头文件；不适用于独立 C++ 或 Objective-C 文件。'
```

### 4. 组织资源

开放格式允许按需添加附加资源，常用约定为：

- `scripts/`：需要确定性执行或每次都会重复实现的代码。
- `references/`：只在特定条件下读取的详细规范和知识。
- `assets/`：生成最终产物所需的模板、图片、字体或数据。

本仓库默认不创建空目录、README、变更日志、占位文件或重复说明；只有 Agent 执行任务确实需要时才增加资源。

### 5. 编写正文并渐进披露

使用命令式、可执行的说明，并按操作风险决定精确程度：

- 给出默认方案，只在条件满足时介绍替代方案。
- 对脆弱、不可逆或顺序敏感的操作给出精确步骤。
- 使用短示例或模板表达固定输出格式。
- 把违反合理预期的事实和常见错误放在 Gotchas 中。
- 需要产出文件时说明输出路径、格式和验证方法。
- `SKILL.md` 只保留每次执行都需要的内容，详细规范放入按需读取的资源。
- 资源使用相对路径并注明读取条件，保持从 `SKILL.md` 直接可达；较长的 reference 提供目录或搜索关键词。

不要重复基础概念或资源内容、罗列大量同等选项，或使用无法验证的“正确处理”“注意质量”等要求。

### 6. 修改或审查现有 Skill

修改或审查前，完整读取 `SKILL.md` 及本次任务需要的直接引用，并检查相关案例、脚本、验证方式和未提交修改。

分别评估格式、触发和输出质量；只修改有证据支持的问题，不顺便重构无关目录。跨客户端审查时，区分开放格式要求和客户端扩展。

## 格式核心

`SKILL.md` 必须包含 YAML Frontmatter 和 Markdown 正文。默认只使用：

```yaml
---
name: skill-name
description: '描述 Skill 做什么，以及什么时候使用'
---
```

`name` 必须满足：

- 长度为 1 至 64 个字符。
- 只包含小写字母、数字和连字符。
- 不以连字符开头或结尾，不包含连续连字符。
- 与父目录名称完全一致。

`description` 必须非空且不超过 1024 个字符。

可选标准字段包括：

- `license`：许可证名称或 Skill 内许可证文件。
- `compatibility`：环境要求，存在时为 1 至 500 个字符。
- `metadata`：字符串键到字符串值的映射。
- `allowed-tools`：实验字段，各客户端支持不一致；跨客户端 Skill 默认不使用。

将 `SKILL.md` 控制在 500 行和约 5000 tokens 以内。客户端专属元数据不得冒充通用字段；官方 [Agent Skills specification](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx) 是格式解释的最终依据，但 Skill 的日常执行不应依赖联网读取它。

## 分级验证

所有修改都必须：

1. 检查目录名、文件名和 Frontmatter。
2. 运行仓库现有 Markdown linter。
3. 环境中存在 `skills-ref` 时运行 `skills-ref validate path/to/skill`。
4. 实际执行所有新增或修改的脚本。
5. 修复发现的问题并重新验证。

新建或大幅修改时，使用“收集证据并定义边界”中收集的正反例检查触发边界、执行过程和最终输出。复杂 Skill 应比较启用和未启用 Skill 的结果，确认 Skill 带来可观察改进。

格式验证只能证明 Skill 可被读取，不能证明它有效。无法执行的验证必须在交付时说明。

## 审查与交付

审查 Skill 时至少报告：

- 格式合规：Frontmatter、命名、目录和通用字段。
- 触发质量：能力描述、正例覆盖和误触发风险。
- 内容质量：流程可执行性、资源分层、关键陷阱和维护成本。
- 验证缺口：已执行、失败或尚未执行的检查。

为问题引用具体文件位置。修改全局 Skill 后还要说明目的、问题证据、跨项目适用性（包括为什么不是项目级内容）及验证结果。
